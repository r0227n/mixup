# OKFクリエイター

提供された知識と根拠からOKFバンドルを作成・保守する。記憶したフィールド名や要件に頼らず、常に最新の仕様を正とする。

## ワークフロー

1. 次のURLから最新仕様を取得する。

   ```text
   https://raw.githubusercontent.com/GoogleCloudPlatform/knowledge-catalog/main/okf/SPEC.md
   ```

2. ユーザーが提供した資料と、既存バンドルがあればその内容を読む。対象のバンドルルート、作業範囲、OKFの対象バージョン、作業種別（新規作成・更新・移行・レビュー）を特定する。
3. 提供された出典で裏付けられる知識だけを抽出する。事実、仮定、未解決事項を区別する。
4. 必要最小限のバンドル構造を設計する。独立して参照する知識単位ごとに1つのコンセプトを作り、将来の憶測ではなくドメインに基づいて整理する。
5. 取得した最新仕様に従い、コンセプト文書、リンク、必要に応じたインデックスとログを作成または編集する。
6. 編集したファイルだけでなく、影響を受けるバンドル全体を検証する。
7. 変更したコンセプトID、使用した仕様バージョン、検証結果、不足している根拠、追加判断が必要な事項を報告する。

仕様を取得できない場合は、利用可能な固定版を使うことについてユーザーの明示的な同意がない限り、OKFファイルを作成・変更せずに停止する。使用するバージョンまたはコミットを明記する。

## 作成ルール

- 予約ファイル以外のすべてのコンセプト文書を、YAMLフロントマター付きのUTF-8 Markdownで記述する。
- 空でない `type` を必ず含める。任意フィールドは、検索性、来歴、信頼性、ライフサイクル、実行方法の理解に役立つ場合だけ追加する。
- 既存文書を更新するときは、未知のフロントマターキーを保持する。
- `type` には、内容を単独で理解できる説明的な値を使う。グローバルな型レジストリを独自に作らない。
- 人とエージェントの両方が読み取りやすいよう、見出し、リスト、表、コードフェンスなどの構造的なMarkdownを優先する。
- コンセプト間リンクには、原則として `/` で始まるバンドルルート相対リンクを使う。サブツリー単位の移植性が重要な場合は相対リンクを使う。
- 最新仕様で求められている場合は、`sources` のエントリとキー付き脚注を使って個別の主張に出典を対応付ける。
- 信頼度スコアを捏造せず、客観的な信頼性シグナルだけを記録する。
- 根拠なしに、生成済み、検証済み、人間レビュー済み、または証明済みと記載しない。裏付けられないメタデータは省略するか、必要に応じてコンセプトをドラフトとして扱う。
- アクター表記と日付・日時形式は、最新仕様に厳密に従う。
- 既存リンクや履歴が依存している非推奨コンセプトは、黙って削除せずライフサイクル状態を明示して保持する。
- ユーザーが修正した内容を保持し、再生成された内容と区別する。

## バンドル構造

- 予約ファイル以外のすべての `.md` ファイルをコンセプト文書として扱う。
- `index.md` は段階的開示のための一覧、`log.md` は時系列の更新履歴として予約する。
- `index.md` は、内容一覧がナビゲーションを実質的に改善する場所にだけ追加する。リンクは配置ディレクトリからの相対パスにし、可能な場合は短い説明を添える。
- `log.md` は、ユーザーが履歴管理を求めた場合、または既存バンドルですでに使われている場合だけ追加する。新しい項目を先頭に置き、仕様準拠の日付見出しを使う。
- バンドルのバージョン宣言は、最新仕様で許可された場所にだけ記述する。
- リンク切れは、ユーザーが全リンクの解決を求めている場合を除き警告として扱う。未知の型、拡張フィールド、任意メタデータの欠落だけを理由に、適合文書を拒否しない。

## Attested Computation

- 認可された計算ごとに、独立した `Attested Computation` コンセプトを作成する。
- このコンセプト型について最新仕様が必須とするフィールドを含める。
- 呼び出し側が値を束縛できる、型付きのパラメーターだけを宣言する。呼び出し側の値で計算自体を変更できる設計にしない。
- 仕様で認められた計算表現のうち1つだけを選ぶ。規約上の見出し以下へインラインで記述するか、パスで参照する。
- 複数の独立して検証される計算を1つのコンセプトへ埋め込まず、説明用のメトリクスやアセットから各計算へリンクする。
- 即興のコードを認可済みとして扱わない。正式な計算、executor、receipt、決定論的attesterの情報が不足している場合は、その不足を記録し、必要な出典または承認を求める。
- 文書の検証と実行単位のattestationを分離する。最新仕様で明示的に変更されない限り、実行時のreceiptをバンドルへ保存しない。

## 更新と移行

1. 編集前に、影響を受けるすべてのコンセプトを読み、リンク、来歴、拡張フィールド、ユーザーの修正を保持する。
2. 宣言されたバンドルバージョンと現在の文書形式を、最新仕様の移行ガイダンスと比較する。
3. コンセプト、インデックス、ログ、参照される計算アセットへ一貫して変更を適用する。
4. ユーザーが移行期間用のバンドルを求めない限り、対象バージョンで置き換えられた互換フィールドを残さない。
5. 来歴、検証、ライフサイクル、計算契約に関する変更を中心に、破壊的変更と意味上の変更を要約する。

## 検証

取得した仕様の規範表現に基づいて適合性を確認する。少なくとも次を検証する。

1. 予約ファイル以外のすべての `.md` ファイルが、解析可能なYAMLフロントマターで始まり、空でない `type` を含むことを確認する。
2. すべての `index.md` と `log.md` が、バンドルルートのインデックスに関する特例を含め、予約ファイルの構造に従っていることを確認する。
3. 使用されている各任意フィールド群について、必須の子キー、データ形状、アクター形式、日付形式を確認する。
4. `Attested Computation` の契約について、必須フィールド、パラメーター宣言、計算の配置、executorのreceipt、決定論的attesterへの参照を確認する。
5. 内部リンクとパス値フィールドを、バンドルのパス規則に従って解決する。仕様上許容されるリンク切れは、適合エラーではなく警告として報告する。
6. 出典表示に使う本文のキー付き脚注が対応する `sources` エントリを持ち、各コンセプト内でsource IDが安定かつ一意であることを確認する。
7. 期限切れまたは非推奨の内容を、不正な形式とは分けて報告する。
8. 未知の型と拡張キーを保持し、エラーとして扱わない。

利用可能な場合は、実際のYAMLパーサーを使う。目視や正規表現だけでYAMLの解析可能性を証明したと主張しない。

## 出力

作成または更新では、次を返す。

- バンドルのパスと変更したコンセプトID
- 使用したOKF仕様のバージョン
- 構造と主要なメタデータ判断の簡潔な説明
- 検証エラー、警告、未解決の根拠不足

レビューのみの場合はファイルを変更せず、適合エラー、意味上のリスク、改善提案の順に、`path:line` 形式で指摘を報告する。各指摘に関連する仕様セクションを示す。
